## ✅ Keep — 잘한 점

### 1. 새로 짜기 전에 진행 상태부터 확인한 것
요청 카드만 보면 처음부터 구현해야 할 것처럼 보였지만, 실제 로컬에는 산책 기록 관련 파일들이 이미 거의 준비돼 있었다. `rg`와 파일 직접 확인으로 어디까지 됐는지 먼저 파악해서, 중복 구현 대신 빠진 정책과 문서 정합성만 채웠다.

### 2. MVP 범위와 Phase 3 범위를 문서에서 분리한 것
기존 API 문서에는 `walkRouteId`, 시작 좌표, `weatherSnapshot`, GPS locations 응답처럼 이번 MVP 범위 밖 필드가 섞여 있었다. 실제 구현은 수동 거리 입력/생략과 이력 조회가 핵심이므로, GPS 트래킹은 Phase 3 보류로 명확히 내려 문서와 코드의 기대치를 맞췄다.

### 3. 완료 기준을 E2E로 확인한 것
카드의 완료 기준인 시작→종료→history, 타인 dog 403, 미종료 중복 시작 409를 `WalkE2ETest`가 직접 검증한다. 테스트가 단순 컨트롤러 단위가 아니라 회원가입·로그인·반려견 등록까지 통과하는 흐름이라 시나리오 3과 잘 맞는다.

### 4. 한글 경로 문제와 코드 문제를 분리한 것
프로젝트 원래 경로에서는 Gradle test worker가 모든 테스트 클래스를 `ClassNotFoundException`으로 못 읽었다. 같은 코드를 `C:\tmp\first-team-project-walk-check-0608`에 복사해 실행하니 `WalkE2ETest`가 통과했다. 코드가 깨진 게 아니라 경로/Gradle worker classpath 문제라는 근거를 남겼다.

## 📚 오늘 새로 배운 것

### 산책 기록 도메인
- **진행 중 산책 정책은 반려견 단위로 잡는 게 자연스럽다** — `findByDogIdAndEndTimeIsNull`로 한 반려견이 동시에 여러 산책을 시작하지 못하게 막았다.
- **종료 시점 duration 자동 계산** — 요청 body에서 시간을 받지 않고 서버 `startTime~endTime` 기준으로 계산해야 조작 가능성이 줄고 E2E도 단순해진다.
- **중복 종료도 정책이 필요하다** — 시작 중복만 막으면 끝이 아니라, 이미 끝난 산책에 `/end`가 다시 들어오는 경우도 409로 명확히 처리하는 편이 낫다.

### 문서 정합성
- **API 예시는 구현 DTO 기준으로 맞춰야 한다** — 오래된 예시 필드가 남아 있으면 프론트가 잘못 붙는다. 이번에는 `WalkResponse` record를 기준으로 문서를 다시 맞췄다.
- **Phase 분리는 표와 본문 둘 다 맞춰야 한다** — 본문에만 "Phase 3 보류"라고 쓰고 목록 표에 ✅가 남아 있으면 모순이다. 마지막 grep으로 표까지 수정했다.

### 검증
- **컴파일 통과와 테스트 실행 통과는 다른 문제** — 원래 경로에서 컴파일은 성공했지만 테스트 worker만 실패했다. 경로 이슈를 분리하려면 같은 코드로 다른 경로에서 재현 여부를 보는 게 유효했다.
